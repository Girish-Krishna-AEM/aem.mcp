## Execution Summary (Addendum: FR-7 Multi-Informer Location Search — added 2026-10-26)
- New requirement: user asked whether the Informer query path supports a list of informers (not just one), and requested support for "find informers near `<location>` within `<radius>` miles" — gathering all matching informers and fetching alerts in parallel, with a token-efficient response.
- Entered via Plan Mode (not a formal AI-DLC Requirements Analysis cycle): 2 parallel Explore passes (Unit 1 data model, Unit 2 query flow) + 1 Plan pass + user clarifying questions (AskUserQuestion) confirmed 4 design decisions, then a written plan was approved via ExitPlanMode before any code was touched.
- **Key decisions**: new dedicated MCP tool `get_informers_near_location` (not an overload of `get_informer_status`, which stays byte-for-byte unchanged); 100-mile radius cap (reuses Unit 2's existing Strike-intent cap constants) with nearest-25 truncation (`truncated`/`totalMatchesInRadius` flags); disabled informers included in results but never alerts-queried (mirrors existing BR-5); response carries counts only (`alertCount`/`siteCount`/`distanceMiles`), never full per-alert detail, for token efficiency.
- **Unit 1**: new `GeoDistanceUtils` (`LightningCommon`) extracted from `StrikeDetectionModule`'s private Haversine methods (pure move, no behavior change); `InformerRecord` gained additive `Latitude`/`Longitude`/`Radius` fields (stub data has them, only ~3% of records are actually geocoded — non-zero — the rest are `(0,0)` and are explicitly excluded from radius matching); new `InformerLocationModels.cs` (request/response/match types, kept separate from the existing single-search types); `InformerStatusModule.GetInformersNearLocationAsync` does the real `Task.WhenAll` parallel fan-out to the Alerts API, with per-item exception handling (one informer's failure doesn't fail the whole request — new BR-20); new tool registered in **both** `McpTools.cs` and `ToolRegistry.cs` (confirmed by reading `Program.cs`/`McpClient.cs` that Unit 2 only ever calls `/mcp/messages` → `ToolRegistry.cs`, so that's the load-bearing path, but both surfaces must stay in parity).
- **Unit 2**: `ParameterExtractor.ExtractInformerParameters` async-ified with a new location-mode branch (detected via existing, already-generic `LocationPhrasePattern` + `RadiusPattern` both matching — reused verbatim, no new regex); `QueryController` gained a `ResolveInformerToolName` resolver (mirrors the existing `ResolveWeatherToolName` precedent) so the Informer intent can route to either of two tool names from one request; `ResultFormatter` gained `BuildInformerListSummary` (counts-only, 1-2 sentences, per [[feedback_lightning_strike_summary_format]] convention).
- **Real bug found and fixed during testing** (not anticipated by the plan): `IntentClassifier`'s Informer pattern only matched singular "informer" (`\binformer\b` — word-boundary fails mid-word on a trailing "s"), so natural plural phrasing like "find informers near X" silently failed to classify at all. Fixed to `\binformers?\b`.
- **Verification**: 79/79 Unit 1 tests + 84/84 Unit 2 tests passing (163 total, up from 140+72 — includes new `GeoDistanceUtilsTests.cs`, extended `InformerStatusModuleTests.cs`, extended `ParameterExtractorTests.cs`, new `ResultFormatterTests.cs` [first-ever dedicated tests for that class], extended `IntentClassifierTests.cs`, extended `CoordinatorIntegrationTests.cs`, extended both Unit 1 integration test files for both MCP surfaces). **Fully live-verified** via Docker Compose (stub mode): new tool via both `/mcp/messages` and `/mcp`, radius-cap rejection (clean 400), existing `get_informer_status` regression-confirmed byte-identical, and full end-to-end `/query` round trip ("Find informers near latitude 30.3085, longitude -82.2741 within 50 miles" → correct tool resolution + counts-only summary).
- New business rules documented: Unit 1 BR-15 through BR-20, Unit 2 BR-15 through BR-18 (see both units' `functional-design/business-rules.md`).

Fixed: `GetPulsesAsync` now takes `latitude`/`longitude`/`radius`/`radiusUnit` and sends `p=<lat>,<lon>&radius=<value><mi|km>` (API requires the unit suffix — a bare number returns `"radius is not valid."`). - **2026-10-08 fix (FR-2/FR-5, Unit 2+1)**: three distinct bugs found investigating "hourly forecast looks wrong" — (1) `IntentClassifier`'s Strike regex matched the generic words `near`/`location`, so ANY "near X" query (including weather queries) was misrouted to the strike tool — fixed by removing those words from the Strike pattern (`strike|lightning|lx` only); (2) `ParameterExtractor`'s `LocationPhrasePattern` swallowed a trailing "in details"/"with details" into the location text, breaking geocoding — fixed by adding it as a recognized stop-phrase; (3) neither daily nor hourly forecast responses exposed the upstream `ForecastCreatedUtc` (when the forecast was generated), so two forecasts fetched minutes apart looked contradictory with no way to tell why — fixed by threading `ForecastCreatedUtc` through `WeatherForecastApiModels`/`DomainModels`/`WeatherForecastModule` and appending `(as of ...)` to the Coordinator's weather summary. Unit 2: 66/66 passing (4 new); Unit 1: 56/56 unaffected. **Fully live-verified** with the user's exact original query end-to-end through Docker Compose.
